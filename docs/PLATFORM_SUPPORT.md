# Platform support (actual implementation, not aspirations)

Studio standard: Hot Attic Games Master Engineering Directive v2.0 (owner-held document; not copied here because this repository is public). It requires **three**
targets for every game: Android APK, Windows x86-64, native Linux x86-64 (Steam Deck / Steam Machine), with Steam as the primary destination.

| Target | Status | Evidence |
| --- | --- | --- |
| Android APK | **Supported.** Expo SDK 54 / React Native 0.81.5 (new architecture, Hermes), arm64-v8a + armeabi-v7a, API 36, debug-keystore signed | `apk-build.yml`; v15 built and inspected (`docs/BRANCH-LEDGER.md` release table); emulator smoke test; no physical test yet |
| Windows x86-64 | **Implemented, packaged, NOT executed.** `Endless Escape Build NN EXE.zip` = the unchanged web export + the Electron shell in `desktop/` (Electron 41.0.0, `EndlessEscape.exe` is a verified PE32+ x86-64 binary). Cross-packaged on a Linux machine; the package has never been run on Windows (no Windows machine or runner was used) | `scripts/desktop/package.mjs`; unit tests in `tests/desktopShell.test.ts`; physical / Windows execution: UNVERIFIED |
| Linux x86-64 | **Implemented, packaged, smoke-tested under xvfb.** `Endless Escape Build NN Linux.tar.gz` (native Electron on x86-64 Linux; `./endless-escape.sh`). The unpacked package was launched for real on a headless Linux machine: game loads from `app://`, works offline, bridge present, save mirror written and restored | `scripts/desktop/smoke.mjs` (also run by the workflow); not tested on a Steam Deck / Steam Machine or with a GPU |
| Steam (Windows / Linux / Deck) | **Readiness work only.** No Steamworks SDK, credentials, Steam Input config, Steam Cloud or SteamPipe upload exist or were attempted. The Chromium Gamepad API already receives Steam Input and the Deck's controls | `docs/STEAM_HARDWARE_CHECKLIST.md`, `docs/DESKTOP.md` |
| Web | not a shipped target; it is the renderer inside the desktop shell. `react-dom`, `react-native-web`, `@expo/metro-runtime` are declared in `package.json`; `app.json` pins `platforms` to android / ios so the Android native fingerprint is unchanged (`tests/desktopShell.test.ts`) | `EXPO_NO_WEB_SETUP=1 expo export --platform web` |

## One codebase
There is one authoritative source line (`release.json` `authoritativeBranch`). Game logic (physics, progression, procedural generation, AI, balance, saves) lives in `src/` and is shared.
Platform-specific code is isolated in three files (`src/util/support.ts`, `textures.ts`, `releaseRuntime.ts`) behind `Platform.OS` / `Platform.select`; native configuration is `app.json` / `app.config.js`.
Build targets are selected by the `platform` input of `apk-build.yml` (`android`, `windows`, `linux` or `all`); a GitHub Release needs `all` so a partial release can never be published. The desktop shell adds no gameplay code:
input mapping for keyboard and controllers lives in `src/desktop/` (web / desktop only; `DesktopLayer.native.tsx` is empty on Android) and only produces the same `input` fields the touch HUD writes (`docs/DESKTOP_INPUT.md`).
The one shared-source touch outside `src/desktop/` is `Platform.OS === 'web'`-guarded accessibility props on the two volume sliders (no Android change).

## Pinned toolchain (Android)
Expo 54.0.33, React Native 0.81.5, React 19.1.0, expo-updates 29.0.16, three 0.166.1 (all from `package-lock.json`); Gradle 8.14.3 (wrapper generated by `expo prebuild`); AGP 8.11.0;
Kotlin 2.1.20; NDK 27.1.12297006 (`scripts/ci/install-ndk.sh`); build tools 36.0.0; minSdk 24, targetSdk / compileSdk 36 (React Native template); JDK Temurin 17; Node 22 (floating minor);
runner image `ubuntu-24.04` for the Android jobs. Each build records these in `build-manifest.json`. AAB capability is preserved (`production-build.yml`, held).

## Desktop approach and why (decision recorded; owner may still override)
Chosen: **Electron shell around the existing Expo web export.** The game already rendered and played in Chromium through the Expo web target, so no engine migration and no gameplay fork were needed: one source line, one set of game logic.
Electron bundles its own Chromium, which gives identical WebGL, audio and Gamepad API behaviour on Windows and Linux (and on the Steam Deck), and the same Chromium the UI checks already ran in. Tauri was not chosen because it uses the
system WebView (WebKitGTK on Linux), whose WebGL and gamepad behaviour varies by machine and which would make Steam Deck behaviour unpredictable. Costs accepted: ~130-155 MB package size and a larger update payload through SteamPipe.
No unacceptable limit was found; nothing here changes the Android runtime (package `com.verbal76.endlessescaspe`, runtime 0.3.0, native fingerprint `b32bf103...` unchanged).
Details: `docs/DESKTOP.md`.
