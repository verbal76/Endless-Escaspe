### 1.4 Play App Signing vs EAS credentials vs the debug-signed APK line
- VERIFIED (search) https://support.google.com/googleplay/android-developer/answer/9842756 and https://developer.android.com/studio/publish/app-signing : Play App Signing uses an **upload key** (you keep; RSA >= 2048; signs the AAB you upload) and an **app signing key** (Google holds; RSA 4096 if Google-generated; signs APKs delivered to users). A lost/compromised **upload key can be reset** by Google (Play Console > App signing > Request upload key reset with a new certificate.pem); the app signing key cannot be replaced for a published app (except by the limited key-upgrade programme - ASSUMPTION).
- VERIFIED (search) https://docs.expo.dev/app-signing/app-credentials/ and https://docs.expo.dev/submit/android-manual/ : with EAS-managed credentials EAS generates and stores the **upload** keystore; Google re-signs with the app signing key; first upload may be done manually in Play Console (App bundles > Upload) - `eas submit` needs a Google service-account JSON key. Docs recommend choosing Google-generated signing key.
- ASSUMPTION (documented behaviour, not re-verified): Play App Signing is mandatory for new apps published as AAB; you may either let Google generate the app signing key or upload your own.
- **Do NOT use the public Expo debug keystore** as the upload key or as an uploaded app-signing key: it ships in every Expo template (see $SP/review2/F.md F-7; README l.131-133; apk-build.yml l.125-133). Anyone could produce an APK with the same signature and read AsyncStorage. Choose a Google-generated app signing key + a fresh upload key (EAS-managed or owner-held keystore).
- Consequence for migration (fact of Android signing; VERIFIED principle in developer.android.com/studio/publish/app-signing): an app installed from the debug-signed GitHub APK has a different certificate from the Play-delivered app (signed by Google's app signing key). Android refuses to install one over the other (INSTALL_FAILED_UPDATE_INCOMPATIBLE); testers must **uninstall** first, which deletes AsyncStorage saves, settings, coins, outfits and the previous-run debug log. Same package name is required for Play, so the two lines cannot coexist on one device. Also: versionCode must increase on Play uploads; the sideload line uses `EE_BUILD_NUMBER` (GitHub run number, app.config.js) - keep Play's versionCode independent (EAS remote appVersionSource is configured in eas.json: `appVersionSource: remote`; the CI uses env instead - pick one source for the Play line).

### 2.2 What data leaves the device today (read from src)
Network: no fetch/XMLHttpRequest/WebSocket/analytics/ads/IAP SDKs in src or package.json (grep). The only network paths:
1. **expo-updates** (app.json updates.enabled, checkAutomatically ON_LOAD, url https://u.expo.dev/702308e3-...): on launch and on manual "check now" (src/util/releaseRuntime.ts checkForNewUpdate) the app contacts Expo's update server; the request carries runtime version, platform, channel header (`expo-channel-name: preview`), current/embedded update ids, and inherently the device IP address (ASSUMPTION about exact headers: documented by Expo; verify in docs.expo.dev/technical-specs/expo-updates-1). No user identifier is added by this code. Downloads JS bundle + assets (code/asset updates).
   - Play-policy flag (ASSUMPTION, NEEDS OWNER CONFIRMATION): Play's Device and Network Abuse policy restricts downloading executable code from outside Play; OTA JS updates via expo-updates are widely used in Play apps (code runs in the JS VM), but the owner should read the policy and decide whether to keep OTA enabled in the Play build.
2. **Bug report / feature request** (src/util/support.ts): composes a mailto: to hotatticgames@gmail.com and opens the user's mail app via Linking.openURL. Body carries: build/update info (app version, versionCode, git SHA, update id, channel, runtime version, OTA state), Platform.OS + Android OS version, texture/font/render-audit rows, and the last 30 entries of the previous-run and current-run debug logs (src/util/debug.ts: log messages and player *save names*). Only transmitted if the user presses send in their mail app (user-initiated; goes through the user's email provider; the user's email address is exposed to the developer by the send). "COPY / SHARE INFO" uses the Android share sheet - same data, user-chosen destination.
3. Local only (not transmitted): AsyncStorage saves (player-entered save names, coins, stars, outfits, endless best, daily best), settings (volumes, toggles), debug log ring buffers. No account, no login, no location, no contacts, no microphone use, no advertising ID, no device identifiers read by app code (expo-application is read for version/build only, not install id).
Not network but third-party code: expo-haptics, expo-keep-awake, expo-gl etc. - no data collection (ASSUMPTION; standard Expo modules).
